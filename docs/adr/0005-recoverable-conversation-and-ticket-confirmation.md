# ADR 0005：领域会话状态恢复与工单确认幂等

- 状态：Accepted
- 日期：2026-08-30

## 背景

首个 Agent 增量只能在单次请求内补参和生成工单草稿。真实支持流程要求客户端复用 `session_id`：缺参后下一轮继续原意图，工单在显式确认后创建，并且超时、重复请求和并发确认不能产生重复副作用。

## 决策

新增 `agent_conversations` 领域表，持久化会话所有者、租户、状态、待处理意图、已提供上下文、工单草稿、工单结果、确认 Key 哈希和版本。每轮 LangGraph 从该表恢复状态：

- `awaiting_clarification` 直接进入 `resume_decision`，不再次调用模型；
- `awaiting_confirmation` 返回原草稿，只有 `confirmation=confirm_ticket` 才写入；
- `confirmation=cancel_ticket` 清除草稿且不产生 Ticket；
- 安全预检拒绝不会破坏已有待补参或待确认状态；
- `session_id` 绑定创建者和租户，其他用户不能接管。

确认请求必须带客户端 `Idempotency-Key`，数据库只保存其 SHA-256。真正传给确定性工单服务的 Key 固定为 `agent-{session_id}`，因此即使工单已提交但会话结果尚未保存，重试或并发确认仍指向同一幂等记录。已完成会话使用相同客户端 Key 返回原结果；更换 Key 返回 409。

## 为什么暂不使用 LangGraph PostgresSaver

当前需要恢复的是业务事实：缺哪些字段、等待什么确认、创建了哪张工单。这些状态需要被 API、审计和人工工作台直接查询，因此先使用显式领域表。LangGraph checkpointer 更适合节点级暂停后从图中间恢复；在引入真正的 interrupt/human-in-the-loop 节点时再增加，避免现在同时维护两套含义重叠的状态。

## 代价与限制

- 会话状态迁移需要应用层维护，并用数据库约束和测试保证一致；
- 当前版本字段用于审计演进，尚未实现通用乐观冲突响应；
- 工单内部幂等键与客户端 Key 分离，需要文档说明；
- 尚不能从任意 LangGraph 节点中间恢复，只能从完整上一轮结果恢复。

## 验证

集成测试覆盖跨请求补参、确认缺 Key、首次创建、相同 Key 重放、换 Key 冲突、取消、跨用户拒绝、安全拒绝后保留草稿，以及两个并发确认只创建一张工单。
